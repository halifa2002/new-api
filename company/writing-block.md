# New API Company Edition
## 公司品牌化二次开发技术方案

**项目定位：** 基于 New API 构建公司自有品牌的 AI API 聚合服务平台。

**设计参考：** SiliconFlow（硅基流动）的产品体验、页面布局和开发者服务模式。

**核心原则：** 官方核心优先、前端独立开发、最小化后端补丁、持续同步官方更新。

---

# 一、项目目标

基于 New API 官方项目进行品牌化二次开发。

保留官方成熟的后端能力和管理员管理功能，重新设计对外服务的网站及用户控制台。

最终形成三个独立的产品界面：

1. 品牌官网：用于展示公司、产品、模型服务和价格。
2. 用户控制台：用于用户注册、登录、API Key 管理、模型查询、用量统计和消费记录。
3. 管理员后台：保留 New API 官方完整管理功能，仅替换 Logo、品牌名称、颜色、图标和必要的视觉元素。

不以重新开发 API 网关为目标，不重写 New API 已有的成熟业务逻辑。

# 二、总体技术架构

采用前后端分离架构。

```text
                  用户访问
                     |
                     v
             公司品牌 Web 平台
                     |
          +----------+----------+
          |          |          |
          v          v          v
        官网       用户控制台   开发者文档
          |          |
          +----------+
                     |
                     v
             API 接口适配层
                     |
                     v
              New API 官方核心
                     |
       +-------------+-------------+
       |             |             |
       v             v             v
      用户管理       渠道管理       模型路由
       |             |             |
       v             v             v
      API Key       额度计费       调用日志
                     |
                     v
                上游模型服务
```

技术边界：

- New API：继续负责核心业务。
- Company Portal：负责官网和用户控制台。
- Admin：继续使用官方管理后台。
- API Adapter：统一处理前端与 New API 的数据交互。
- Reverse Proxy：负责域名、HTTPS、静态资源及 API 转发。

前端不得直接访问数据库。

不得在浏览器中保存管理员密钥或管理员 Token。

不得为了 UI 方便而绕过 New API 原有的权限校验。

# 三、代码仓库与 Git 管理

这是保证官方持续更新最重要的部分。

建议采用两个独立 Git 仓库。

## 3.1 New API 核心仓库

```text
company-new-api/
├── upstream/
│   └── 官方仓库远程引用
├── company-patches/
│   ├── branding/
│   └── extensions/
├── deploy/
├── tests/
├── Dockerfile
└── README.md
```

不要求将上述目录强行放进官方目录结构。`company-patches` 可以位于独立补丁仓库，重点是确保补丁可追踪、可重复应用。

Git 远程：

- upstream：New API 官方仓库。
- origin：公司维护的 Fork 仓库。

分支策略：

```text
upstream/main       官方同步基线
main                公司稳定发行版本
develop             公司开发分支
release/*           公司发布分支
```

实际同步时应以官方正式 Release Tag 和固定 Commit SHA 为基准，不直接无条件追随官方开发主分支。

## 3.2 品牌前端仓库

```text
company-portal/
├── apps/
│   ├── website/              # 品牌官网
│   └── console/              # 用户控制台
│
├── packages/
│   ├── api-client/           # New API 接口封装
│   ├── ui/                   # 统一 UI 组件
│   ├── design-tokens/        # 品牌设计变量
│   └── types/                # API 数据类型
│
├── docs/                     # 开发者文档
├── tests/
├── deploy/
└── README.md
```

官网和用户控制台可以部署在同一个前端工程中，但应保持路由、模块和权限边界独立。

## 3.3 官方代码修改原则

必须遵守：

1. 不直接修改官方核心业务逻辑。
2. 不大面积修改官方前端组件。
3. 不随意更改官方数据库结构。
4. 不删除官方已有功能。
5. 公司自定义代码必须独立提交。
6. 所有公司修改必须能够明确追踪。
7. 官方升级时尽量通过 Cherry-pick、Rebase 或可重复补丁应用完成。
8. 不允许直接将公司代码覆盖到新版本官方代码上。
9. 不允许依靠手工复制文件完成版本升级。
10. 每次升级必须保留旧版本回滚能力。

特别注意：管理员后台如果没有官方提供的主题配置能力，可以使用一个非常小的独立品牌补丁进行修改。不得为了品牌化重构整个管理员后台。

# 四、UI 产品设计方案

整体参考 SiliconFlow 的产品设计语言。

不是直接复制页面，而是学习其：

- 清晰的导航层级。
- 简洁的视觉布局。
- 开发者优先的设计。
- 模型卡片和模型详情页。
- 价格展示。
- 用量数据可视化。
- 快速 API 接入体验。

## 4.1 品牌官网

建议页面：

### 首页

主要内容：

- 顶部品牌导航。
- 产品介绍。
- 平台能力介绍。
- 核心模型展示。
- 服务优势。
- API 接入示例。
- 定价入口。
- 开发者入口。
- 注册和登录入口。

首页应重点展示平台提供什么服务，而不是单纯展示技术宣传。

### 模型服务页面

展示：

- 模型分类。
- 模型名称。
- 模型厂商。
- 模型用途。
- 模型能力。
- 输入价格。
- 输出价格。
- 上下文长度。
- API 调用方式。
- 模型详细介绍。

模型数据应由经过整理的公开模型目录提供，并与实际可用模型及价格保持一致。

### 定价页面

展示：

- 不同模型价格。
- 输入 Token 价格。
- 输出 Token 价格。
- 不同模型的计费规则。
- 价格说明。
- 常见问题。

必须以实际后端计费规则为准，不能只在前端写死价格。

### 文档页面

包括：

- 快速开始。
- API Key 获取。
- OpenAI 兼容接口。
- 模型调用示例。
- 请求参数。
- 错误码。
- 常见问题。

## 4.2 用户控制台

用户控制台是本次 UI 二开的重点。

### A. 用户首页 Dashboard

展示：

- 当前账户余额。
- 今日消费。
- 本月消费。
- 总调用次数。
- Token 使用量。
- API Key 数量。
- 最近调用记录。
- 常用模型。
- 消费趋势图。

要求数据真实来自后端，不允许使用静态模拟数据冒充正式统计。

### B. 模型广场

展示：

- 全部模型。
- 模型分类。
- 模型搜索。
- 模型能力标签。
- 输入价格。
- 输出价格。
- 模型详情。
- API 调用代码示例。

分类可根据实际模型能力建立，例如：

- 通用对话。
- 推理模型。
- 编程模型。
- 图像模型。
- 视频模型。
- Embedding。
- 音频模型。

只有实际接入并验证的能力才能展示为可用服务。

### C. API Key 管理

支持：

- 创建 API Key。
- 删除 API Key。
- 查看 API Key 状态。
- 设置名称。
- 设置额度（需核实官方实际支持的粒度）。
- 设置模型权限（需核实官方实际支持范围）。
- 查看创建时间。
- 查看最后使用时间。

安全要求：

- 新创建的 Key 仅在必要时完整展示一次。
- 后端正确存储密钥摘要或按官方机制安全保存。
- 前端不得记录完整密钥到日志。
- 删除操作需要二次确认。
- 所有操作必须经过后端身份和权限校验。

### D. 用量统计

展示：

- 每日调用量。
- 每日 Token 用量。
- 每日消费。
- 模型维度统计。
- API Key 维度统计。
- 请求成功率。
- 调用明细。

需要明确时间范围、时区、统计口径和分页规则，避免前端自行累加与后端账单不一致。

### E. 消费记录

展示：

- 消费时间。
- 模型名称。
- Token 使用量。
- 输入 Token。
- 输出 Token。
- 消费金额。
- 请求状态。
- 关联请求标识。

### F. 账户设置

包括：

- 用户资料。
- 账户安全。
- 密码修改。
- 账户状态。
- 登录记录（如后端支持）。

### G. 充值和余额

如果当前 New API 版本有对应充值能力，优先沿用。

如果后续需要新增支付系统，单独设计订单、支付回调和账本，不得通过直接修改余额字段的方式完成充值。

本阶段不擅自增加未经验证的支付逻辑。

# 五、管理员后台

管理员后台必须保留 New API 官方原有的完整功能。

包括但不限于：

- 用户管理。
- 渠道管理。
- 模型管理。
- 令牌管理。
- 额度管理。
- 兑换码或充值管理（如官方版本提供）。
- 消费日志。
- 数据统计。
- 系统设置。
- 权限管理。

本阶段只做：

1. 替换品牌 Logo。
2. 替换平台名称。
3. 修改 favicon。
4. 修改主色调。
5. 统一按钮与基础视觉样式。
6. 调整必要的登录页面视觉。
7. 保持原有导航、交互和业务功能。

不改变任何官方业务流程。

管理员后台应与用户控制台分开部署或至少分开路由，并可增加 VPN、IP 白名单或额外身份验证保护。

# 六、API Adapter 设计

不要让 Company Portal 到处直接编写 New API 的原始请求。

统一建立 API Client：

```text
packages/api-client/
├── auth.ts
├── models.ts
├── tokens.ts
├── usage.ts
├── billing.ts
├── account.ts
├── client.ts
└── types.ts
```

原则：

1. 统一处理请求认证。
2. 统一处理错误码。
3. 统一处理分页。
4. 统一处理时间和金额格式。
5. 统一定义 TypeScript 类型。
6. 不在页面组件内部重复编写接口请求。
7. 对官方接口进行契约测试。

先审查当前锁定版本的官方接口实现，确认每个功能是否已有接口。

如果接口不存在：

- 优先检查是否有现成官方能力可以组合。
- 其次开发独立 BFF 或最小扩展 API。
- 避免修改已有核心计费、鉴权和渠道路由逻辑。
- 如必须修改官方后端，建立独立补丁和自动化测试。

禁止通过直接查询 New API 内部数据库来绕过其 API 权限体系。

# 七、设计规范

## 7.1 视觉方向

参考 SiliconFlow 的现代 AI SaaS 风格。

推荐：

- 浅色主题为默认主题。
- 深色文字和浅色背景。
- 蓝色或靛蓝色作为品牌强调色，具体色值由设计阶段确定。
- 留白充足。
- 页面信息层级明确。
- 卡片边框轻量化。
- 适度使用圆角。
- 图表简洁。
- 控制台避免过多装饰性元素。

## 7.2 统一设计系统

在 design-tokens 中统一维护：

- Brand Color。
- Typography。
- Spacing。
- Border Radius。
- Shadow。
- Button。
- Input。
- Table。
- Card。
- Modal。
- Navigation。

禁止每个页面自行定义一套颜色和间距。

## 7.3 响应式要求

至少覆盖：

- 桌面端 1440px。
- 笔记本 1280px。
- 平板端。
- 手机端 390px。

手机端优先保证账户信息、API Key、模型查询及用量查看功能可用。

# 八、官方持续更新机制

这是项目的强制性工程要求。

## 8.1 版本管理

每个公司发行版本必须记录：

```text
Company Edition Version
New API Upstream Version
New API Commit SHA
Company Patch Version
Portal Version
Database Migration Version
Docker Image Tag
```

不允许只记录公司自己的版本号。

必须能够准确还原某次生产部署使用的官方代码版本。

## 8.2 官方同步流程

每次同步按以下流程执行：

```text
获取官方 Release
       |
       v
记录官方 Tag 和 SHA
       |
       v
创建升级分支
       |
       v
同步官方代码
       |
       v
重新应用公司补丁
       |
       v
解决代码冲突
       |
       v
编译及单元测试
       |
       v
API 契约测试
       |
       v
用户核心流程测试
       |
       v
管理员后台功能测试
       |
       v
测试环境部署
       |
       v
人工验收
       |
       v
生产环境发布
```

## 8.3 自动化检查

每次升级至少检查：

- 官方后端是否能够正常编译。
- 公司前端是否能够正常构建。
- 登录是否正常。
- 用户信息查询是否正常。
- API Key 创建和删除是否正常。
- 模型列表是否正常。
- 模型实际调用是否正常。
- 额度和消费统计是否一致。
- 消费明细是否正常。
- 管理员登录是否正常。
- 管理员渠道管理功能是否正常。
- Docker 镜像是否正常构建。
- 数据库升级是否成功。

## 8.4 升级回滚

正式升级前：

1. 数据库完整备份。
2. 记录当前镜像版本。
3. 记录当前 Commit SHA。
4. 记录当前数据库迁移版本。
5. 在测试环境完成升级验证。

升级失败后能够恢复旧版本服务。

数据库迁移必须考虑向前兼容和回滚策略，不能简单认为恢复旧 Docker 镜像就一定能恢复旧数据库。

# 九、测试与验收标准

## 9.1 功能验收

官网：

- 首页能够正常访问。
- 模型目录能够正常展示。
- 模型价格与实际计费一致。
- 文档示例可实际调用。

用户控制台：

- 注册和登录正常。
- 用户资料正常。
- API Key 创建及删除正常。
- 模型权限正常。
- 用量统计正常。
- 消费记录正常。
- 余额展示与官方后台一致。

管理员后台：

- 原有官方功能保留。
- Logo 和品牌名称正确。
- 原有管理流程不受影响。

## 9.2 接口验收

至少验证：

- 正常认证。
- 无权限访问。
- 失效 Token。
- 无效 API Key。
- 请求超时。
- 上游报错。
- 模型不可用。
- 超出额度。
- 并发请求。
- 分页和时间范围。

## 9.3 官方同步验收

这是独立的验收项目：

- 能够获取官方更新。
- 能够识别官方版本变化。
- 能够重新应用公司补丁。
- 能够识别代码冲突。
- 能够运行升级测试。
- 能够生成升级报告。
- 能够回滚到上一稳定版本。

不能只以新版本部署成功作为官方同步合格标准。

工作：

3. 核实官方技术栈。

5. 核实官方 API 路由。

7. 核实管理员权限体系。
8. 核实官方前端主题配置能力。
9. 检查官方许可证及第三方依赖许可。
10. 建立官方同步机制。

交付物：

- 官方架构审计报告。
- 官方 API 接口清单。
- 数据库结构报告。
- 二开边界说明。
- Git 管理方案。
- 升级验证方案。

交付物：

- 可运行的品牌官网。

# 十一、明确禁止事项

1. 不允许直接把 New API 改造成完全无法跟随官方升级的深度 Fork。
2. 不允许把公司所有业务都写进 New API 核心。
3. 不允许删除或破坏官方管理员功能。
